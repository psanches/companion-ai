# Lumi Medical Demo · Ativa Parkinson

An isolated, synthetic-only demonstration. Patient “Helena Exemplo” and all five records are invented. This folder does not import the existing Lumi Worker, bind its databases, or open its medical routes.

## Available behavior

- Fictional patient profile, chronological records, prescriptions, laboratory table, reports.
- Accent-insensitive full-text search across titles, document text, types, and authors; type filters.
- Valid one-page downloadable PDFs, in-app viewer plus download/native Android viewer fallback.
- PDF import into browser memory only. SHA-256 exact-byte allowlist accepts only the original sample PDFs generated by this demo; rejects real, modified, or oversized documents. Maximum five samples, duplicates prevented. Files never leave the browser and disappear on reload/reset/removal.
- Server-side OpenAI Responses explanations in Brazilian Portuguese, with three predefined questions and server-owned fictional context only. Prepared explanations are separately labeled and are never presented as AI output.
- Desktop/mobile CSS, large-text control, keyboard focus, status announcements, no service-worker cache.

## Isolated deployment only

**Never run the root repository deploy command. Never use the root wrangler.jsonc.**

1. Sign in to the user's Cloudflare account using `npx wrangler login` or deploy through an authorized account integration.
2. From this folder, run `npm run deploy`. This creates only `lumi-ativa-medical-demo` and its dedicated budget Durable Object. Configuration has no domain routes, existing services, KV or R2 bindings. Requires Durable Object support in the account.
3. Configure `OPENAI_API_KEY` as a secret on this new Worker, securely reusing the user-authorized Lumi Research key. Do not paste the key into chat. Existing Cloudflare secrets cannot be read/exported; the owner must retrieve the original key through their secure key manager or supply it directly to the new Worker's secret field.
4. Configure `DEMO_ACCESS_CODE` on this new Worker as a secret, at least 20 characters. Deliver it privately to the presenter outside source control. Use it in the AI section to start a four-hour HttpOnly, Secure, SameSite=Strict HMAC session.
5. Use the workers.dev URL returned by the new deployment as the isolated demo preview. Do not add `mylumicompanion.com` routes. Do not replace `lumi-develop`.
6. On the hosted URL verify profile/search, download/reimport a sample PDF, arbitrary PDF rejection, document viewing on desktop and Android, access-code login, and a live AI response. Confirm existing Lumi remains unchanged.

CLI secret configuration (interactive, values are not command arguments):

```
npx wrangler secret put OPENAI_API_KEY --config wrangler.jsonc
npx wrangler secret put DEMO_ACCESS_CODE --config wrangler.jsonc
```

## Cost and privacy controls

- Dedicated persistent global budget Durable Object: max 50 upstream requests/day (UTC), atomic reservation before calling OpenAI. Failed/time-out requests consume budget. Concurrent requests cannot bypass the reservation count.
- Fixed synthetic input and three question IDs; 500 max output tokens; 25-second timeout; cached successful replies per scenario/question daily. At most 15 distinct cached answers per day.
- `store:false`; no request body/credential logging. This setting does not guarantee zero provider retention; provider-side processing and applicable retention still apply to synthetic data.
- No arbitrary text, freeform chat, server uploads, real-patient database, or credential UI in the frontend. Search stays local. Imported document bytes are not uploaded.
- AI requires access code and same-origin POST. Login attempts have global limit 100/day. A shared code is demo protection, not patient identity or clinical authorization. Expiration/rotation revokes sessions. Login cap can be exhausted by hostile requests; use Cloudflare Access/rate limiting for a broader audience.
- Strict CSP, no-store, no CORS permissions; existing medical/API/history/memory/chat routes denied; unknown routes never proxy to Lumi.
- API keys and access code reside only in the new Worker's server secrets. The shared API key's provider/project quota is shared with Lumi Research; the demo's budget does not isolate project billing.

## GitHub deployment alternative (when dashboard sign-in is unavailable)

Configure these four **repository Actions secrets** directly in GitHub Settings → Secrets and variables → Actions. Never paste values into chat, source files, workflow inputs, or logs:

- `ATIVA_CLOUDFLARE_API_TOKEN`: token for the chosen Cloudflare account with Worker script deployment and Durable Object management permissions. Limit its account scope and lifetime; it is a deployment credential, not a patient-data credential.
- `ATIVA_CLOUDFLARE_ACCOUNT_ID`: that account's identifier.
- `ATIVA_OPENAI_API_KEY`: the user-authorized existing Lumi Research key.
- `ATIVA_DEMO_ACCESS_CODE`: private presenter code, at least 20 characters.

The `Ativa isolated preview deployment` workflow runs only on `feature/ativa-medical-demo`, only when the workflow or `ativa-demo/preview-deploy.json` changes. Missing credentials cause an explicit **no-deployment** summary rather than an attempted deploy. After configuring secrets, increment `request` in that marker on this demo branch to trigger deployment. It runs the existing 139 security tests, demo tests and build before calling the isolated deploy script. No credentials appear in CLI arguments or logs. OpenAI smoke verification uses only the fixed synthetic consultation and consumes at most one upstream call, within the budget.

Do not merge this workflow to production or change its branch/name/config guards. Root Lumi and medical staging Workers are never deployed by it. A green skipped deployment is not a working preview; use the returned URL and explicit successful HTTP/AI summary as deployment evidence.
